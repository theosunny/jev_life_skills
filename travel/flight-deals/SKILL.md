# Flight Deals — 机票比价与购买方案

目标:给定出发地、目的地、日期约束,产出「可直接下单」的购票方案,而不是一个孤立的价格数字。

## 前置条件(开工前 30 秒检查)

1. **浏览器**:`browser-use` 可用(daemon 活着、Chrome 已授权远程调试)。不可用先跑 `browser-use --doctor`。
2. **TypeSafe key**:找 `TYPESAFE_API_KEY` 环境变量,或项目目录 `.env`。都没有就请用户提供并写入 `.env`(不要让用户把 key 粘贴到对话里)。没有 key 时可以完成抓取与比价,但跳过 Jev 判断并明说。
3. 携程无需登录也能查价;但若触发验证码/登录墙,停下来问用户,不要自行处理账号。

## 第一步:需求澄清(一次问齐,别挤牙膏)

必填参数,缺哪个问哪个:

| 参数 | 示例 | 默认(用户没说时) |
|---|---|---|
| 出发城市 | 北京 / 天津 / 多选 | 问 |
| 目的地 | 大阪 / 东京 / "北海道全域"→用门户机场札幌 SPK | 问 |
| 单程还是往返 | 往返 | 问 |
| 日期约束 | 固定日期 / 区间+间隔(如"间隔6-8天,9/25后走,10/11前回") | 问 |
| 人数与舱位 | 1成人经济舱 | 1 成人经济舱 |
| 偏好 | 预算优先 / 体验优先 / 可接受红眼中转 | 中立,输出时分档 |

用户说"最划算"却没给日期时,按"未来可出行窗口内的低价组合"处理,并在报告里声明假设。

## 第二步:双路扫价(核心方法论)

**必须同时比两条路,只比一条会得出错误结论**(实测案例:直飞往返套票 ¥7,000+,但去程直飞+回程中转分开买只要 ¥5,428;反过来双中转套票有时又比分开买便宜):

- **路 A:往返套票** —— URL 模板 `https://flights.ctrip.com/online/list/round-{dep}-{arr}?depdate={D1}_{D2}&cabin=y_s&adult=1&child=0&infant=0`
- **路 B:分开买单程** —— `https://flights.ctrip.com/online/list/oneway-{dep}-{arr}?depdate={D}&cabin=y_s&adult=1&child=0&infant=0`,去程、回程各查

扫价策略(高效且防限流):

1. **先探测路线有效性**:每条路线查一次间隔中值的组合,确认城市代码对(标题会回显"X到Y机票")。
2. **利用低价日历**:结果页"自由搭配往返组合"日历**跟随当前查询的间隔**展示邻近组合价格,一次查询拿 ~7 个组合;单程页自带 7 天单程日历。用它覆盖日期面,不要逐组合硬查。
3. **控制节奏**:同 tab 内 URL 跳转可行,但连续快速查询会触发限流(症状与对策见 references/ctrip-harvest.md)。查询间隔 ≥3 秒,批量扫描放后台并打印实时进度(`sys.stdout.reconfigure(line_buffering=True)`),每次脚本别超过 ~8 次查询。
4. **甜点区优先**:中国节假日(国庆/春节/五一)当周贵,节后错峰显著便宜。先扫节后组合,再补边界日期。

抓取细节(城市代码表、DOM 选择器、正则、限流对策、UI 兜底流程)读 **references/ctrip-harvest.md**。

## 第三步:口径修正(不做这步结论必错)

携程列表价是「起价」,订单页实付普遍上浮(实测 +26%)。修正方法按优先级:

1. 用户实测过订单价 → 直接用,并以此校准其他价格的上浮比例。
2. 无实测 → 起价 × 1.25–1.3 标注为"推断实价",报告中明确区分「起价 / 推断实价 / 实测实价」三种口径。

同时核对:余票(很多最低档"剩1张")、廉航行李额(香港快运/春秋/越航托运另购,¥200-400)、中转签证(首尔转机过境需签证,香港/河内转机一般无需)。

## 第四步:Jev 结构化判断

把 top 5-8 个候选方案发给 Jev(`jev-latest`)做两个并行问题:

1. **choice「最划算」**:criteria = 每个方案的完整描述(价格口径、航班、时刻、直飞/中转、红眼、余票、目的地价值一句话)。
2. **noul「关键权衡」**:通常是该次决策最纠结的一对(如"多付 ¥X 买直飞值不值"、"为省 ¥Y 忍受红眼值不值")。

state 里放全部结构化数据与背景(节假日、目的地特征);置信度 <0.5 时如实告诉用户"这是偏好敏感的选择",同时给分档建议而不是单一答案。

请求模板、state 结构、响应解读读 **references/jev-judgment.md**。每次调用的 `usage` 字段要累计,写进最终报告。

## 第五步:输出报告(固定结构)

```
# 往返 {出发}⇄{目的地} 机票方案({日期窗口})

## 结论(一句话 + 推荐方案)
## 方案总览表(方案/日期/总价[口径]/构成/Jev 评估)
## 分档推荐:💰省钱档 / ⚖️均衡档 / 🛌舒适档(各含航班号、起降时刻、机场、票价)
## 购买步骤(每档可照做的操作序列)
## ⚠️ 下单必读(实价口径、波动、余票、行李、签证、分开买无联程保障)
## Token 账单(Jev 各次调用 input/output,累计)
```

**输出载体(按此顺序选择,不依赖任何特定平台):**

1. 默认:报告直接在对话中输出,同时保存为 `flight-report-{YYYYMMDD}.md` 到当前目录 —— 纯 Markdown,任何环境可用
2. md 交付后**主动询问一次**:「需要同步生成飞书文档吗?」—— 给用户低成本升级入口;只问这一次,用户没回应或拒绝就到此为止,不重复追问
3. 用户要飞书且 `lark-cli auth status` 已登录:用 lark-doc skill 写入飞书(数据用表格,价格口径写在表内)
4. 用户要飞书但环境未配置:交付 md 文件并告知配置方法(`lark-cli auth login`),不阻塞交付

## 第六步(可选):旅游攻略生成

用户要"攻略""行程""怎么玩"时,基于已选机票方案生成攻略,让航班信息驱动行程设计:

1. **内容由你撰写**(景点/美食/行程是通识,Jev 是判断型模型不生成正文)。要点:
   - Day 1 从**航班落地时刻**倒推(09:40 落地 → 下午首个景点;22:20 落地 → 当天只安排住宿)
   - 天数 = 行程间隔;返程航班时刻决定最后一天节奏
   - 含:每日行程、交通(机场↔市区)、美食清单、预算表(机票+住宿+餐饮+门票)、贴士
2. **Jev 可选介入**:景点多于可安排天数时,用 choice 让 Jev 按用户偏好(人文/自然/美食/亲子)做取舍,置信度解读同第四步。
3. **输出形态矩阵**(用户要哪种给哪种,默认 HTML + PNG):
   - Markdown:`guide-{目的地}-{日期}.md`
   - HTML:单文件内联样式,设计要求见 references/guide-output.md(反模板化,选明确风格方向)
   - PNG:HTML 用 browser-use 打开后 CDP 截图,方法见 references/guide-output.md
   - 飞书文档:lark-doc,图片用 `docs +media-insert` 插入

## 红线

- 价格必须标口径(起价/推断/实测),不标口径的价格报告是错的。
- 抓取失败/被限流的数据缺口要如实标注"未取到",不许编造补齐。
- 不代替用户下单;涉及支付、账号操作一律停下来。
